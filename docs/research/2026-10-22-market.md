# Исследование ниши: llm-endpoint-scanner

Дата: 2026-10-22. Статус данных: факты подкреплены ссылками; где подтверждение
не найдено, стоит пометка «не найдено» или «гипотеза».

---

## 1. Резюме

- Ниша «DAST для LLM/AI-приложений» валидирована рынком: волна M&A 2025 года
  (Check Point ← Lakera ~$202M, Palo Alto ← Protect AI, F5 ← CalypsoAI $180M,
  Zscaler ← SplxAI), терминология «DAST-AI» закреплена (Mindgard), Gartner
  прогнозирует рост «AI-amplified security» с $49B (2026) до $204B (2030).
- Прямые DAST-first конкуренты (Mindgard, SplxAI, Repello) — enterprise
  SaaS без публичных цен и self-serve. Open-source лидеры (garak, PyRIT,
  promptfoo) либо model-центричны, либо требуют программирования, либо
  завязаны на облако/LLM-судью.
- Самая подтверждённая боль пользователей (5 независимых источников) —
  **неточная детекция: false positives/negatives и необходимость ручного
  триажа**. Вторая (4 источника) — **боль подключения внутренних/нестандартных
  API** (недокументированные конфиги, молча игнорируемые опции, обязательные
  API-ключи). Обе — прямое попадание в наше позиционирование (layered-детекция
  с confidence + чистый декларативный YAML для произвольного HTTP endpoint).
- Наши главные пробелы против востребованного: нет compliance-маппинга
  (OWASP LLM Top 10 / MITRE ATLAS) в отчётах, нет выбора категорий/проб для
  CI, нет пользовательских декларативных проб, нет LLM-as-judge (опционально),
  нет multi-endpoint sweep (при этом «несколько сервисов — куда смотреть
  в первую очередь» — наш же основной сценарий из спеки §2).

## 2. Текущее состояние инструмента (аудит кода, 2026-10-22)

Версия 1.0.0, ~2650 строк Python, 61 тест, CI (pytest 3.10–3.13, Semgrep,
TruffleHog). Все требования спеки закрыты: REQ-C1..C4, FR-1..FR-6, NFR-1..5,
майлстоуны M1–M4.

**Умеет:** 6 категорий атак (17 проб, 27 запросов/скан с baseline);
layered-детекция (burst → leakage patterns → canary → refusal → baseline →
консервативный fallback) с методом и confidence на каждый вердикт; JSON +
Markdown отчёты с triage «look here first»; `--dry-run`; `--fail-on` для CI;
декларативный YAML для произвольного JSON-тела запроса; mock-сервер в двух
режимах; секреты только из env и никогда в отчётах.

**Не умеет (по коду и спеке):** multi-turn (явный out of scope, Spec §3);
стриминг/WebSocket/gRPC; OAuth/динамическая аутентификация (только статические
заголовки); LLM-as-judge; выбор подмножества категорий из CLI; пользовательские
payload'ы из конфига; HTML/SARIF-отчёты; сравнение сканов/история; параллельное
сканирование нескольких endpoint'ов; retry/backoff; пробы только на английском.
Инструмент полностью синхронный и последовательный.

## 4. Конкуренты

### 4.1 Open-source (метрики GitHub API на 22.10.2026)

#### garak (NVIDIA) — 9 636 stars, Apache-2.0, релиз v0.17.1 (16.10.2026), ежедневные коммиты
([GitHub](https://github.com/NVIDIA/garak))

- 80+ проб: dan, encoding, promptinject, latentinjection, leakreplay, atkgen,
  tap, goat, packagehallucination и др.; маппинг на OWASP LLM Top 10 / MITRE
  ATLAS ([StationX](https://app.stationx.net/articles/garak-llm-scanner),
  [aisecbench.com](https://aisecbench.com/posts/best-llm-red-teaming-tools-2026/)).
- **Произвольный HTTP endpoint: да** — RestGenerator с шаблоном запроса,
  заголовками, JSONPath, rate-limit retry, mTLS
  ([документация](https://reference.garak.ai/en/latest/garak.generators.rest.html)).
- Multi-turn: ограниченно (atkgen/tap/goat требуют атакующей LLM)
  ([bestaisecuritytools.com](https://bestaisecuritytools.com/posts/garak-vs-pyrit-llm-red-teaming/)).
- Отчёты: JSONL + hitlog + HTML; CI — ручной парсинг JSONL
  ([arXiv:2406.11036](https://pdf.arxiv.org/pdf/2406.11036),
  [bestllmscanners.com](https://bestllmscanners.com/posts/automated-llm-red-teaming-in-ci-garak-pyrit-promptfoo/)).
- Сильные: самый большой каталог проб, зрелость, активная разработка.
  Слабые: полный прогон — часы; детекторы keyword-based с высоким FP/FN;
  документация REST-генератора сломана churn'ом CLI (см. §5).

#### PyRIT (Microsoft) — 4 668 stars, MIT, v1.1.0 (04.09.2026)
([GitHub](https://github.com/microsoft/PyRIT); старый `Azure/PyRIT` заархивирован 27.03.2026)

- Фреймворк оркестрации: targets, converters, scorers, orchestrators
  (PromptSending, RedTeaming, Crescendo, TAP)
  ([документация](https://azure.github.io/PyRIT/)).
- **HTTP endpoint: да** (HTTPTarget), но скореры требуют LLM-доступа
  ([QASkills](https://qaskills.sh/blog/pyrit-ai-red-teaming-framework-guide-2026)).
- **Multi-turn: лучший среди всех** — stateful кампании с feedback loop
  ([RedTeamingOrchestrator](https://azure.github.io/PyRIT/_autosummary/pyrit.orchestrator.RedTeamingOrchestrator.html)).
- Отчёты: memory-слой (БД), готового генератора отчётов нет — DIY
  ([arXiv:2410.16527](https://arxiv.org/html/2410.16527v1)).
- Слабые: высочайший порог входа (Python-код, свой .env, DuckDB), Azure-
  центричность, LLM-судья удорожает прогон в 2–4×
  ([aramgrc.com](https://www.aramgrc.com/blog/garak-vs-pyrit-vs-promptfoo),
  [aisecbench.com](https://aisecbench.com/posts/best-llm-red-teaming-tools-2026/)).

#### promptfoo (OpenAI) — 26 252 stars, MIT, ежедневные коммиты
([GitHub](https://github.com/promptfoo/promptfoo))

- Eval-фреймворк + red team: плагины по категориям вреда + 15+ стратегий
  (jailbreak:tree, crescendo, goat, hydra, multilingual, base64…), OWASP-
  пресеты ([promptfoo multi-turn docs](https://www.promptfoo.dev/docs/red-team/strategies/multi-turn/)).
- **HTTP endpoint: да** (HTTP provider, кастомные JS/Python-провайдеры)
  ([Fortbridge](https://fortbridge.co.uk/llm-red-teaming-promptfoo-custom-provider/)).
- **Нюанс:** генерация adversarial-промптов по умолчанию идёт в облако
  api.promptfoo.dev ([issue #1969](https://github.com/promptfoo/promptfoo/issues/1969));
  подтверждена отправка промптов/истории/email при заявленном «100% local»
  ([issue #5808](https://github.com/promptfoo/promptfoo/issues/5808)).
- Цены: Community бесплатно до 10k probes/мес; Enterprise — custom
  ([pricing](https://www.promptfoo.dev/pricing/)). Куплен OpenAI (09.03.2026).
- Сильные: лучший DX, YAML, web-отчёт «который не стыдно показать клиенту»,
  нативный GitHub Action, OWASP/NIST/MITRE-маппинги
  ([aramgrc.com](https://www.aramgrc.com/blog/garak-vs-pyrit-vs-promptfoo),
  [CI docs](https://www.promptfoo.dev/docs/integrations/ci-cd/)).

#### Giskard — 5 916 stars, Apache-2.0, v3.0.1
([GitHub](https://github.com/Giskard-AI/giskard))

- Скан security + quality (hallucination, bias); генерация тестов из описания
  бизнес-контекста ([legacy docs](https://legacy-docs.giskard.ai/en/latest/open_source/scan/scan_llm/)).
- **HTTP endpoint: через Python-обёртку**, и scan **обязательно требует
  API-ключ внешнего LLM-судьи** ([PyPI](https://pypi.org/project/giskard/)) —
  не подходит для air-gapped / строгого black-box.
- Слабые: нет CLI, 3.5 ГБ на диске, Python ≤3.12, Hub — цены не публичны
  ([StationX](https://app.stationx.net/articles/giskard)).

#### FuzzyAI (CyberArk) — 1 587 stars, Apache-2.0, **последний коммит 06.02.2026**
([GitHub](https://github.com/cyberark/FuzzyAI))

- ~18 jailbreak-атак (PAIR, Crescendo, ActorAttack, ArtPrompt…); REST-
  провайдер через raw HTTP-файл; судья может быть полностью локальным
  (Ollama/HF). Слабые: узкий фокус (только jailbreak), нет отчётности и CI,
  проект выглядит заброшенным.

#### DeepTeam (Confident AI) — 3 035 stars, Apache-2.0
([GitHub](https://github.com/confident-ai/deepteam))

- 40–50+ типов уязвимостей, 10+ атак, multi-turn модуль; цель —
  `model_callback` (может ходить по HTTP), есть YAML CLI
  ([docs](https://docs.confident-ai.com/docs/red-teaming-vulnerabilities)).
- Судья — LLM через deepeval (в quickstart нужен OPENAI_API_KEY).
- Облако: Starter $200/мес, Team $2 000/мес; red-team модуль — только
  Enterprise-аддон ([pricing](https://www.confident-ai.com/pricing)).

## 7. Пробелы и выводы

**Table stakes (есть у большинства, обязательно иметь):** black-box HTTP,
декларативный конфиг, пригодные отчёты, CI-интеграция, compliance-маппинг,
multi-turn как направление. У нас закрыто всё, кроме compliance-маппинга и
multi-turn (осознанно out of scope).

**Востребовано, но у нас отсутствует:**
1. Compliance mapping (OWASP LLM Top 10 / MITRE ATLAS) в отчётах — драйвер
   EU AI Act/NIST; хвалят promptfoo, жалуются на ручной маппинг у garak/PyRIT.
2. Выбор категорий/проб из CLI — нужно для CI (скорость, стоимость,
   предсказуемость); у garak есть `--probes`.
3. Пользовательские декларативные пробы — отвечает боли «инструмент не знает
   мой домен» и «статические пробы протухают».
4. LLM-as-judge как опциональный слой — самая подтверждённая боль рынка
   (неточная детекция); у нас детекция честная, но чисто эвристическая сверх
   канареек.
5. Multi-endpoint sweep — наш основной сценарий из Spec §2 («несколько
   сервисов — куда смотреть сначала») сейчас требует N ручных прогонов.
6. HTML/SARIF-отчёты — promptfoo хвалят за «отчёт, который не стыдно показать
   клиенту»; SARIF даёт нативную интеграцию с GitHub Code Scanning.

**Дифференциаторы (где выделяться):**
- Честная layered-детекция с confidence + verbatim evidence — против «стены
  JSONL» и FP-шума garak (5 подтверждений боли).
- 100% офлайн по умолчанию, без телеметрии и облачной генерации — против
  promptfoo #5808 и обязательных судей у Giskard/DeepTeam.
- «10 минут до триажа N сервисов» — фиксированный лёгкий прогон против
  многочасовых кампаний garak/PyRIT.
- Стабильный CLI/конфиг без churn — против сломанных туториалов garak.

**Делать НЕ стоит:**
- Multi-turn/agentic кампании — здесь PyRIT вне конкуренции, это рушит
  обещание «10 минут», кратно удорожает скан и противоречит Spec §3.
  Оставить out of scope, явно указав границу.
- Runtime guardrails/WAF — другой рынок (Lakera, F5), другая модель
  развёртывания.
- Model scanning / supply chain — ниша Protect AI/HiddenLayer, требует
  доступа к артефактам модели (против нашего black-box позиционирования).
- SaaS-платформа с дашбордами и аккаунтами — ломает NFR-4 (offline) и
  масштаб проекта; историю сканов закрыть локальным сравнением отчётов.
- Полные evals качества модели (hallucination, bias) — территория Giskard.

### Топ-5 на ближайшую итерацию (обоснование)

1. **F1 (compliance mapping)** — low сложность, high ценность; прямой
   регуляторный драйвер; закрывает table stakes, где мы единственные «❌».
2. **F2 (выбор прогона + бюджет запросов)** — low сложность; делает CI-гейт
   (наш existing `--fail-on`) реально удобным; отвечает подтверждённой боли
   стоимости/скорости.
3. **F3 (пользовательские пробы из конфига)** — medium сложность; бьёт сразу
   в две подтверждённые боли (доменная специфика + протухание статических
   корпусов) и усиливает главный дифференциатор «конфигурация вместо кода».
4. **F4 (опциональный LLM-judge)** — medium сложность благодаря Judge
   Protocol; отвечает боли №1 рынка (неточная детекция) без разрушения
   офлайн-по-умолчанию (opt-in).
5. **F5 (multi-endpoint sweep)** — medium сложность; реализует на практике
   главный сценарий продукта («несколько сервисов — куда смотреть сначала»),
   который сейчас заявлен в спеке, но не автоматизирован.

F6 (SARIF/HTML) — следующим шагом после топ-5; F7 включить в работу над F5
(сweep без retry хрупок). F8–F10 отложить до подтверждения спроса.
